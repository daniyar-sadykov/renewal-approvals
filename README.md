# renewal-approvals

Согласование и выполнение заявок на продление ресурсов. Инициатор создаёт заявку на продление ресурса на 30 дней, согласующий одобряет или отклоняет её. После одобрения фоновый обработчик отправляет операцию провайдеру (локальный имитатор) и после подтверждения сдвигает срок ресурса ровно один раз.

Стек: TypeScript, NestJS 11 (API и фоновый обработчик), React 19 и Vite 8 (интерфейс), PostgreSQL 18 (драйвер `pg`, SQL без ORM), Jest и supertest (тесты).

Проверено на Windows 10 Pro (19045) со следующими версиями:

| Что | Версия |
|---|---|
| Node.js | 24.13 (требование в `package.json`: 22.12 и новее) |
| npm | 11.6 |
| Python (только имитатор провайдера) | 3.14, без сторонних пакетов |
| PostgreSQL | 18.6, встроенный: npm-пакет `embedded-postgres` 18.6.0-beta.19 с настоящими бинарниками PostgreSQL |

## Запуск с нуля

Все команды выполняются из корня репозитория. Понадобятся четыре терминала: база, имитатор, приложение и один для разовых команд.

### 1. Зависимости

```
npm ci
```

Ставит зависимости всех частей (npm workspaces: `apps/api`, `apps/web`) строго по `package-lock.json`, вместе с бинарниками PostgreSQL для вашей платформы (пакет `@embedded-postgres/<платформа>`).

Файл `.env` не нужен: значения по умолчанию рабочие. Если нужно что-то поменять, скопируйте пример и правьте копию:

```
cp .env.example .env
```

(в PowerShell: `Copy-Item .env.example .env`). Переменные, заданные в самом окружении, важнее значений из `.env`.

### 2. База

Терминал 1:

```
npm run db:start
```

Первый запуск создаёт кластер в каталоге `.pgdata/` (он в `.gitignore`), роль приложения `renewals` и две базы: `renewals` (приложение) и `renewals_test` (тесты). База слушает `127.0.0.1:5433` и работает, пока открыт терминал. Готовность видна по строке `[db:start] готово`.

Остановка: Ctrl+C в этом терминале или из любого другого:

```
npm run db:stop
```

Свой PostgreSQL вместо встроенного: задайте `DATABASE_URL` (и `TEST_DATABASE_URL` для тестов, имя базы должно содержать `test`). Формат строки подключения есть в `.env.example`. Роль должна владеть обеими базами: миграции создают таблицы и расширений не требуют.

Запасной путь через Docker: `docker-compose.yml` поднимает PostgreSQL 18 с той же ролью, теми же базами и тем же портом 5433. Этот путь **не проверен**: на машине разработки Docker нет, файл ни разу не запускался.

```
docker compose up -d
npm run db:reset
```

### 3. Миграции и начальные данные

Терминал 4, при работающей базе:

```
npm run db:reset
```

Пересоздаёт схему `public` в базе из `DATABASE_URL`, применяет все миграции из `db/migrations/` и заливает `db/seed.sql`: пространства Alpha и Beta, три ресурса, четыре учётные записи. **Все данные в этой базе удаляются.** Этой же командой база возвращается в исходное состояние перед повторной проверкой.

Отдельные шаги:

```
npm run db:migrate
npm run db:seed
```

`db:migrate` применяет только ещё не применённые миграции (учёт в таблице `schema_migrations`). `db:seed` идемпотентен: возвращает пространства, ресурсы и учётки к исходным значениям, заявки не трогает.

### 4. Имитатор провайдера

Терминал 2:

```
npm run simulator
```

Запускает `tools/provider_simulator.py` (файл из задания, без правок) на `127.0.0.1:8091` через `scripts/simulator.mjs`. Интерпретатор выбирается сам: переменная `PYTHON`, если задана; иначе на Windows `python`, затем `py`; на остальных системах `python3`, затем `python`. Годится первый, у кого `--version` завершается без ошибки (заглушка `python` из Microsoft Store отсеивается). Не нашёлся ни один: команда завершается с текстом, что указать в `PYTHON`. Данные имитатора живут только в памяти: после его перезапуска все операции и ключи пропадают. Остановка: Ctrl+C.

### 5. Приложение

Терминал 3:

```
npm run dev
```

Поднимает два процесса:

- API на `http://127.0.0.1:3000/api` (проверка: `http://127.0.0.1:3000/api/health`). Пересобирается и перезапускается при правке кода.
- Интерфейс на `http://127.0.0.1:5173`. Vite проксирует `/api` на API, поэтому cookie сессии живёт на одном адресе с интерфейсом.

Открыть в браузере: `http://127.0.0.1:5173`.

**Фоновый обработчик работает в том же процессе, что и API.** Отдельно его запускать не нужно. Отключить: `WORKER_ENABLED=false` (заявки тогда одобряются, но к провайдеру не уходят, пока обработчик не включат снова).

Собранный вариант, без пересборки на лету:

```
npm run build
npm run start -w apps/api
```

`npm run build` собирает API в `apps/api/dist` и интерфейс в `apps/web/dist`. `npm run start -w apps/api` запускает собранный API (с обработчиком). Собранный интерфейс отдаёт `npm run preview -w apps/web` на `http://127.0.0.1:4173` с тем же прокси `/api`. Интерфейс в режиме разработки при собранном API: `npm run dev -w apps/web`.

Остановка приложения: Ctrl+C. На Windows после Ctrl+C иногда остаётся процесс `node`, который держит порт. Проверка, что порт свободен (пустой вывод):

```
netstat -ano | findstr :3000
```

Если строка `LISTENING` осталась, завершите процесс по PID из последнего столбца: `taskkill /PID <pid> /T /F`.

## Настройки

Все переменные необязательны. Их читают API (`apps/api/src/config.ts`), скрипты базы (`scripts/lib/config.mjs`), Vite (`apps/web/vite.config.ts`) и тесты. Источник: окружение, затем `.env` в корне.

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `PGPORT` | `5433` | порт встроенного PostgreSQL; из него же строятся адреса баз по умолчанию |
| `DATABASE_URL` | роль `renewals`, пароль `renewals`, `127.0.0.1:PGPORT`, база `renewals` (строка в `.env.example`) | база приложения и команд `db:migrate`, `db:seed`, `db:reset` |
| `TEST_DATABASE_URL` | то же, база `renewals_test` | база тестов; имя обязано содержать `test`, тесты стирают в ней данные |
| `HOST` | `127.0.0.1` | адрес, на котором слушает API |
| `PORT` | `3000` | порт API; по нему же Vite строит адрес прокси |
| `PROVIDER_BASE_URL` | `http://127.0.0.1:8091` | адрес провайдера (имитатора) |
| `PROVIDER_RETRY_DELAY_MS` | `15000` | пауза после неудачной попытки перед следующим шагом (GET по ключу, затем POST при необходимости); окно, в которое можно остановить приложение |
| `PROVIDER_TIMEOUT_MS` | `5000` | таймаут одного запроса к провайдеру вместе с чтением тела |
| `PROVIDER_MAX_POST_ATTEMPTS` | `3` | сколько POST без подтверждения до «Требует внимания», не меньше 1 |
| `WORKER_ENABLED` | `true` | фоновый обработчик в процессе API: `true`/`1` или `false`/`0` |
| `WORKER_POLL_MS` | `1000` | как часто обработчик ищет готовую задачу, когда очередь пуста |
| `WORKER_LEASE_MS` | `2 * PROVIDER_TIMEOUT_MS + 10000` (20000) | аренда задачи: пока не истекла, задачу не возьмёт другой обработчик; не меньше `2 * PROVIDER_TIMEOUT_MS + 1000`, иначе API не стартует. В `.env.example` закомментирована: без неё аренда считается от таймаута и следует за `PROVIDER_TIMEOUT_MS` |
| `COOKIE_SECURE` | `false` | `true` добавляет флаг `Secure` к cookie сессии; включать, когда API отдаётся по https (по http браузер такую cookie не сохранит) |
| `WEB_PORT` | `5173` | порт Vite в режиме разработки |
| `API_PROXY_TARGET` | `http://127.0.0.1:PORT` | куда Vite проксирует `/api` |
| `PYTHON` | не задана: на Windows `python`, затем `py`; на остальных `python3`, затем `python` | чем `npm run simulator` и тесты запускают имитатор |

Неверное значение числовой переменной или `WORKER_ENABLED` останавливает запуск API с понятным текстом. `COOKIE_SECURE` включается только строкой `true`, любое другое значение означает «выключен».

## Тесты

Перед запуском:

- база поднята (`npm run db:start`); тестовая база `renewals_test` создаётся при первом `db:start` сама;
- **порт 8091 свободен.** Тесты сами запускают свежий имитатор и останавливают его. Если ваш имитатор из шага 4 запущен, остановите его, иначе тесты упадут с текстом «Порт 8091 уже занят». По той же причине тесты нельзя гонять в двух местах одновременно;
- приложение из шага 5 тестам не мешает: они поднимают своё внутри процесса Jest и в порт 3000 не ходят.

```
npm test
```

Тесты идут последовательно (`jest --runInBand`) против настоящей PostgreSQL. Они сами пересоздают схему в `renewals_test` (тем же скриптом, что `db:reset`), база приложения `renewals` не затрагивается. Всего 17 файлов и 130 тестов, на машине разработки прогон занимает около 70 секунд.

## API

Полное описание моделей, полей и ошибок: [`docs/api.md`](docs/api.md). Ниже кратко.

Базовый путь `/api`, тела JSON. Даты `YYYY-MM-DD`, моменты времени ISO 8601 в UTC, суммы целым числом копеек. Сессия: cookie `renewals_session` (`HttpOnly`, `SameSite=Lax`, 7 дней). Пользователь и права берутся только из сессии; `userId`, `workspaceId`, `status` и подобные поля в теле и query сервер не читает.

Формат любой ошибки:

```json
{ "error": "forbidden", "message": "Нет доступа к этому ресурсу" }
```

`error` это код для программы, `message` текст для человека.

| Метод и путь | Кто может | Ответ | Основные ошибки |
|---|---|---|---|
| `POST /api/auth/login` | любой | 200, пользователь и членства, cookie | 400 `validation_error`, 401 `unauthorized`, 429 `too_many_attempts` |
| `POST /api/auth/logout` | вошедший | 204, cookie сброшен | 401 |
| `GET /api/auth/me` | вошедший | 200, пользователь и членства | 401 |
| `GET /api/resources` | вошедший | 200, ресурсы своих пространств с активной заявкой и флагом `canCreateRequest` | 401 |
| `GET /api/resources/:id` | член пространства ресурса | 200, ресурс и все его заявки | 401, 403 `forbidden`, 404 `not_found` |
| `POST /api/resources/:id/renewal-requests` | инициатор пространства | 201, заявка `pending` | 401, 403, 404, 409 `active_request_exists` |
| `GET /api/renewal-requests` | вошедший | 200, заявки своих пространств, новые сверху | 401 |
| `GET /api/renewal-requests/:id` | член пространства заявки | 200, заявка и история | 401, 403, 404 |
| `POST /api/renewal-requests/:id/approve` | согласующий, заявка не своя | 200, заявка `processing` | 401, 404, 403, 409 `invalid_transition`, 409 `resource_changed` |
| `POST /api/renewal-requests/:id/reject` | согласующий, заявка не своя | 200, заявка `rejected` | 401, 404, 403, 409 `invalid_transition` |
| `POST /api/renewal-requests/:id/retry` | согласующий, заявка не своя | 200, заявка `processing` | 401, 404, 403, 409 `invalid_transition` |
| `GET /api/health` | любой | 200 `{ "status": "ok", "database": "up" }` | 503 `database_unavailable` |

У действий над заявкой проверки идут в порядке 401, 404, 403, 409: пользователь без права не узнаёт, в каком состоянии чужая заявка. Тело у POST не нужно, присланное игнорируется: сумму, даты, автора и ключ задаёт сервер.

### Защита запросов

Код: `apps/api/src/app.setup.ts`, `apps/api/src/auth/login-throttle.service.ts`, `apps/api/src/auth/session.service.ts`.

- **Чужой сайт.** Изменяющий запрос (всё, кроме `GET`, `HEAD`, `OPTIONS`, включая вход) с `Origin`, чей хост с портом не совпадает с `Host`, или с `Sec-Fetch-Site: cross-site` получает 403 `forbidden`. Запрос без `Origin` (curl, серверный клиент) проходит. Прокси Vite `Host` не подменяет, поэтому интерфейс не задет.
- **Только JSON.** Тело изменяющего запроса принимается только с `Content-Type: application/json`; форма, `text/plain`, `multipart` дают 400 `validation_error`. Запрос без тела проходит.
- **Перебор паролей.** После 10 неудачных входов по одному логину за минуту (окно от первой неудачи) вход по нему закрыт до конца окна даже с верным паролем: 429 `too_many_attempts` с заголовком `Retry-After`. Успешный вход счётчик сбрасывает. Счётчик живёт в памяти процесса.
- **Сессии.** Каждый вход удаляет просроченные сессии всех пользователей; у пользователя остаются 10 последних сессий, более старые вытесняются.
- **Заголовки.** На всех ответах `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store`; `X-Powered-By` нет.

## Модель состояний заявки

| Состояние | Код | Смысл |
|---|---|---|
| На согласовании | `pending` | создана инициатором, ждёт решения |
| Отклонена | `rejected` | отклонил согласующий; провайдер не вызывается, срок не меняется |
| Выполняется | `processing` | одобрена, задача отправки провайдеру в очереди |
| Завершена | `completed` | провайдер подтвердил, срок ресурса сдвинут один раз |
| Требует внимания | `needs_attention` | подтверждения нет или оно не годится; нужен человек |

```
                 reject (согласующий)
   pending  ------------------------------->  rejected
      |
      | approve (согласующий): одобрение и задача одной транзакцией
      v
   processing  ---------------------------->  completed
      |    ^      подтверждение провайдера
      |    |      (обработчик)
      |    |
      |    | retry (согласующий): тот же ключ, первым шагом GET
      |    |
      v    |
   needs_attention
      ^
      | обработчик: 3 POST без подтверждения (attempts_exhausted),
      | отказ провайдера 4xx (http_409, http_400), несовпадение
      | подтверждения (provider_mismatch), срок ресурса изменился
      | после одобрения (resource_changed)
```

Активные состояния: `pending`, `processing`, `needs_attention`. Конечные: `rejected`, `completed`. Перехода `needs_attention -> completed` напрямую нет, только через повтор. Любой другой переход по API даёт 409 `invalid_transition`.

## Бизнес-правила и где они закреплены

- **Продление на 30 календарных дней от текущего срока.** Новый срок считает база (`expires_on + 30`) при создании заявки, под блокировкой строки ресурса (`apps/api/src/renewals/renewals.service.ts`).
- **Снимок суммы и дат.** Прежний срок, новый срок и сумма записываются в заявку при создании и дальше не меняются. Тело запроса к провайдеру строится только из снимка, поэтому для одной заявки оно всегда одинаковое.
- **Сверка со снимком при одобрении.** Под блокировкой заявки и ресурса срок, стоимость и валюта ресурса сравниваются со снимком. Не совпали: 409 `resource_changed`, заявка остаётся `pending`, провайдер не вызывается (`renewal-decisions.service.ts`).
- **Одна активная заявка на ресурс.** Два рубежа: проверка под блокировкой строки ресурса в сервисе (409 `active_request_exists`) и частичный уникальный индекс `renewal_requests_one_active_per_resource` по `resource_id` с условием `status in ('pending', 'processing', 'needs_attention')` (`db/migrations/0002_renewal_requests.sql`). Если гонку выиграет индекс, нарушение тоже превращается в 409.
- **Свою заявку нельзя одобрить, отклонить или повторить.** Проверка в сервисе (403) и check `renewal_requests_not_self_decided` в базе: `decided_by` не может совпасть с `created_by`.
- **Повторное решение и недопустимый переход: 409.** Заявка берётся `select ... for update`, переход делается условным `update ... where status = <ожидаемый>`. Из параллельных одобрений успешно ровно одно, второе видит уже не `pending`.
- **Одобрение и задача отправки одной транзакцией.** Вторую задачу на ту же заявку не даёт `provider_jobs.request_id unique`.
- **Изоляция пространств.** Пространство берётся из самой сущности (ресурса или заявки), право проверяется по таблице `memberships`. Чужой ресурс или заявка по известному ID: 403. Несуществующий ID (или не uuid у заявки): 404.
- **Деньги и даты.** Стоимость целым числом копеек (`integer`), валюта только `RUB` (check в базе), срок типа `date` без времени.

## Интеграция с провайдером

Код: `apps/api/src/provider/` (клиент `provider.client.ts`, обработчик `renewal-worker.service.ts`, транзакции задачи `provider-jobs.service.ts`).

### Ключ операции

Ключ идемпотентности `renewal-<id заявки>` создаётся вместе с заявкой, хранится в `renewal_requests.idempotency_key` (unique) и никогда не меняется: ни при повторной попытке, ни после перезапуска, ни при повторе согласующим.

Где увидеть:

- в интерфейсе: карточка заявки, поле «Ключ операции», рядом кнопка «Скопировать»;
- в API: поле `idempotencyKey` в ответе `GET /api/renewal-requests/:id` (и в любом ответе с заявкой);
- у имитатора: `GET http://127.0.0.1:8091/renewals/<ключ>`.

### Что уходит провайдеру

```
POST /renewals
Idempotency-Key: renewal-<id заявки>
Content-Type: application/json

{ "resource_id": "res-a-01", "period_months": 1, "amount_minor": 128000, "currency": "RUB" }
```

Тело собирается только из снимка заявки. Имитатор принимает период в месяцах, продление на 30 дней передаётся как `period_months: 1`.

### Шаг обработчика

Обработчик раз в `WORKER_POLL_MS` берёт одну готовую задачу из `provider_jobs` и делает шаг. Сетевые запросы идут только вне транзакций базы. У пула базы свои таймауты (ожидание соединения 5 секунд, один SQL-запрос 10 секунд), оба меньше аренды по умолчанию: зависшая база не держит шаг, запрос API и остановку процесса.

1. **Захват.** `update ... from (select ... for update skip locked limit 1)`: задача `queued`, срок `next_run_at` наступил, аренды нет или она истекла. Ставится `lease_until = now() + WORKER_LEASE_MS`; это значение служит меткой аренды. Все дальнейшие изменения задачи идут с условием `lease_until = <метка>`, поэтому обработчик, у которого аренду уже перехватили, ничего не испортит.
2. **Заявка уже не `processing`** (например, завершена другим путём): задача закрывается, к провайдеру не ходим.
3. **Проверка перед отправкой.** Если POST по этой задаче уже уходил (`post_attempts > 0`) или это первый шаг после повтора согласующим (`verify_before_post`), сначала `GET /renewals/<ключ>`. GET попыткой не считается.
   - 200 с операцией: завершение (шаг 6), нового POST нет;
   - 4xx (кроме 404): «Требует внимания»;
   - попытки исчерпаны: «Требует внимания» с кодом `attempts_exhausted`;
   - 404 или GET без ответа: идём к POST с тем же ключом.
4. **Учёт попытки до отправки.** Отдельной транзакцией `post_attempts = post_attempts + 1`. Сначала запись, потом отправка: если процесс упадёт после отправки, факт попытки не потеряется, и следующий шаг начнётся с GET.
5. **POST** с тем же ключом и тем же телом:
   - 200 с операцией: завершение;
   - **неопределённый ответ** (503 и другие 5xx, таймаут `PROVIDER_TIMEOUT_MS`, обрыв соединения, нечитаемое тело или тело больше 64 КБ, которое дальше не читается): результат неизвестен, операция у провайдера могла выполниться. Задача откладывается на `PROVIDER_RETRY_DELAY_MS`, аренда снимается, в заявку пишется `lastErrorCode` (`http_503`, `timeout`, `network_error`, `bad_response`), в историю событие `provider_error` вида `http_503, попытка 1 из 3`. Статус остаётся `processing`. Следующий шаг начнётся с GET (шаг 3);
   - 4xx (например, 409 «тот же ключ с другим телом»): повтор с тем же телом бессмыслен, сразу «Требует внимания» с кодом `http_409` или `http_400`.
6. **Завершение.** Подтверждение сверяется с заявкой: статус операции `completed`, `resource_id`, сумма, валюта и `period_months`. Не совпало: «Требует внимания» с кодом `provider_mismatch`, срок не сдвигается. Совпало: одной транзакцией заявка `processing -> completed` с `providerOperationId`, срок ресурса `oldExpiresOn -> newExpiresOn`, задача `done`, событие `completed` с `operation_id`.

### «Требует внимания» и повтор

После `PROVIDER_MAX_POST_ATTEMPTS` (3) попыток POST без подтверждения и последнего GET, который тоже ничего не нашёл, заявка уходит в `needs_attention` с кодом `attempts_exhausted`, задача в состояние `failed`. Ресурс остаётся занятым: новую заявку на него создать нельзя (409 `active_request_exists`), пока эта не разрешится.

Согласующий пространства (не автор заявки) нажимает «Повторить отправку» (`POST /api/renewal-requests/:id/retry`). Одной транзакцией: заявка `needs_attention -> processing`, `lastErrorCode` обнуляется, счётчик POST с нуля, флаг `verify_before_post`, событие `retry_requested`. Ключ и тело прежние. Первым шагом обработчик спрашивает GET по ключу: если операция у провайдера уже есть, заявка завершается без нового POST.

### Восстановление после перезапуска

Всё состояние задачи в базе: `post_attempts`, `next_run_at`, `lease_until`, `verify_before_post`, `state`; ключ и тело в заявке. В памяти процесса ничего нужного для продолжения нет.

- **Штатная остановка** (Ctrl+C, SIGTERM): обработчик не берёт новых задач, текущий шаг дорабатывает до конца (он ограничен таймаутами провайдера), пул базы закрывается последним.
- **Остановка в паузе после 503:** задача лежит с `next_run_at` в будущем и без аренды. После запуска, когда пауза истечёт, обработчик видит `post_attempts > 0`, спрашивает GET по тому же ключу, получает сохранённую операцию и завершает заявку. Второго POST и второй операции нет.
- **Процесс умер посреди шага:** аренда истечёт через `WORKER_LEASE_MS`, после чего задачу возьмёт любой живой обработчик. Попытка уже учтена, поэтому шаг начнётся с GET.

### Защита от дублей

- Один ключ на заявку, неизменный: провайдер видит повторы как одну операцию.
- `provider_jobs.request_id unique`: одна задача на заявку, даже при параллельных одобрениях.
- Захват задачи `for update skip locked` плюс аренда с меткой: одну задачу одновременно ведёт один обработчик.
- Условные `update ... where status = 'processing'` и `where state = 'queued' and lease_until = <метка>`: устаревший шаг ничего не меняет.
- Финализация одной транзакцией под блокировкой заявки и ресурса. Повторная обработка не находит заявку в `processing` и только закрывает задачу.
- Срок ресурса сдвигается условием `where expires_on = <прежний срок из снимка>`. Если срок к моменту подтверждения уже другой (изменён после одобрения), он не сдвигается, заявка уходит в «Требует внимания» с кодом `resource_changed`, `providerOperationId` сохраняется.

### Что пишется в историю и лог

- История заявки (`request_events`): `created`, `approved`, `rejected`, `retry_requested` с автором; `provider_error`, `completed`, `needs_attention` от системы (автор пустой). В `detail` только короткий код, номер попытки и `operation_id`.
- Лог API: id заявки, код результата, номер попытки, `operation_id`. Ключ идемпотентности в лог не пишется: он виден в заявке (интерфейс и API).
- Не пишутся нигде: тело и заголовки ответа провайдера, пароли, токены сессий. В базе сессий лежит только sha256 токена. Детали внутренних ошибок 500 только в лог, наружу общий текст.

Коды `lastErrorCode` и `detail` с пояснениями: таблица в [`docs/api.md`](docs/api.md#коды-lasterrorcode). Интерфейс показывает рядом с кодом понятный текст.

## Проверка с перезапуском руками

Сценарий повторяет шаги 4 и 5 контрольного сценария: первая отправка получает 503, приложение останавливается, после запуска заявка завершается тем же ключом, у имитатора одна операция. Автоматически то же самое проверяют `11-restart-recovery.spec.ts` и `18-acceptance.spec.ts`.

Для этого сценария API удобнее держать в отдельном терминале от интерфейса: перезапускается только API, а страница в браузере остаётся.

1. База поднята (`npm run db:start`). Чистые данные:

   ```
   npm run db:reset
   ```

2. Свежий имитатор (если был запущен, остановите Ctrl+C и запустите снова), терминал 2:

   ```
   npm run simulator
   ```

3. Сборка и запуск API с длинной паузой после 503 (60 секунд), терминал 3.

   PowerShell:

   ```
   npm run build
   $env:PROVIDER_RETRY_DELAY_MS = "60000"
   npm run start -w apps/api
   ```

   bash:

   ```
   npm run build
   export PROVIDER_RETRY_DELAY_MS=60000
   npm run start -w apps/api
   ```

   Переменная живёт в этом терминале, повторный запуск в нём же её сохранит.

4. Интерфейс, терминал 4:

   ```
   npm run dev -w apps/web
   ```

   Открыть `http://127.0.0.1:5173`.

5. Войти как `initiator.alpha`. У ресурса «Хранилище A» (`res-a-01`, срок 01.03.2027) нажать «Продлить на 30 дней». Заявка `pending`, срок ресурса прежний.
6. Выйти, войти как `approver.alpha`. Открыть заявку («Подробнее»), нажать «Одобрить». Заявка `processing`. Скопировать ключ операции из карточки.
7. Через секунду-две в истории карточки появится событие «Провайдер не подтвердил попытку» с пояснением «Провайдер ответил ошибкой сервера, результат неизвестен (http_503), попытка 1 из 3», а в терминале API строка `Заявка <id>: http_503, попытка 1 из 3` (id заявки, ключа в логе нет). Имитатор операцию уже сохранил, но ответил 503. Срок «Хранилище A» в списке по-прежнему 01.03.2027.
8. В течение 60 секунд остановить API: Ctrl+C в терминале 3. Убедиться, что порт свободен:

   ```
   netstat -ano | findstr :3000
   ```

   Вывод должен быть пустым (если нет, см. остановку приложения в разделе «Запуск с нуля»). Имитатор не трогать. Пока API остановлен, интерфейс при обновлении показывает «Сервер недоступен», это ожидаемо.
9. У имитатора операция уже есть (в PowerShell именно `curl.exe`, в bash просто `curl`):

   ```
   curl.exe http://127.0.0.1:8091/renewals/<ключ>
   ```

   Ожидается `"status":"completed"`, `"started_count":1`.
10. Запустить API снова в том же терминале 3:

    ```
    npm run start -w apps/api
    ```

    Сессия в браузере сохранилась (сессии хранятся в базе). Пока не истекла пауза в 60 секунд, отсчитанная от момента 503, заявка `processing`, а срок «Хранилище A» прежний, 01.03.2027. Когда пауза истечёт, обработчик спросит GET по тому же ключу, получит сохранённую операцию и завершит заявку без нового POST. В истории появится «Провайдер подтвердил, срок продлён» с номером операции, заявка `completed`, срок «Хранилище A» 31.03.2027.
11. Проверка у имитатора:

    ```
    curl.exe http://127.0.0.1:8091/renewals/<ключ>
    curl.exe "http://127.0.0.1:8091/stats?resource_id=res-a-01"
    ```

    Ожидается `"started_count":1` у операции и `"operation_count":1` по ресурсу. `operation_id` у операции совпадает с полем «Операция провайдера» в карточке. По другим ресурсам `operation_count` равен 0.

### «Требует внимания» и повтор руками

1. `npm run db:reset`, имитатор **остановлен**.
2. API с короткой паузой, чтобы не ждать: в PowerShell `$env:PROVIDER_RETRY_DELAY_MS = "3000"`, в bash `export PROVIDER_RETRY_DELAY_MS=3000`, затем `npm run start -w apps/api`.
3. `initiator.alpha` создаёт заявку на `res-a-01`, `approver.alpha` одобряет.
4. Провайдер недоступен: три попытки с кодом `network_error` (история «попытка 1 из 3», «2 из 3», «3 из 3»), затем заявка «Требует внимания» с причиной `attempts_exhausted`. Карточка объясняет, что случилось и что делать. У ресурса новую заявку создать нельзя.
5. Запустить имитатор (`npm run simulator`). Под `approver.alpha` нажать «Повторить отправку». Заявка `processing`, событие «Повтор отправки запрошен». Обработчик спросит GET (404), отправит POST тем же ключом (503, операция сохранена), после паузы GET вернёт операцию: заявка `completed`, срок 31.03.2027, у имитатора `operation_count: 1`.

Под `initiator.alpha` или `universal.alpha` (если заявку создал он) кнопки повтора нет, карточка поясняет, кто может повторить.

## Интерфейс

Одна страница, адрес экрана в хэше: обновление страницы оставляет на том же экране.

- **Вход.** Логин и пароль, список тестовых логинов с кнопкой «Подставить логин». Неверный пароль, пустые поля и недоступный сервер показываются текстом у формы.
- **Список** (`#/`): шапка с пользователем, пространством и ролями, кнопка «Выйти». Таблица ресурсов: название, пространство, срок, стоимость, активная заявка (значок статуса, ссылка на карточку), кнопка «Продлить на 30 дней» только при `canCreateRequest`. Таблица заявок со сводкой (всего, ожидают, выполняется, требует внимания): ресурс, автор, срок был и станет, сумма, статус, у «Требует внимания» причина с кодом, кнопки «Одобрить», «Отклонить», «Повторить отправку» строго по флагам сервера, ссылка «Подробнее».
- **Карточка заявки** (`#/requests/<id>`): все поля снимка, автор и кто решил, моменты создания, решения и завершения, ключ операции и номер операции провайдера с кнопкой копирования, последняя ошибка текстом и кодом, действия, история событий с автором (или «Система»), переходом и пояснением. У «Требует внимания» блок «Что случилось» и «Что делать».
- **Состояния:** загрузка (скелет), пустые списки с подсказкой, ошибка загрузки с кнопкой «Повторить», ошибка действия текстом сервера рядом с кнопкой (после 409 экран перечитывается), 401 возвращает на вход с сообщением. Пока есть заявки `processing`, список и карточка обновляются сами раз в 2,5 секунды (только при видимой вкладке).
- **Доступность:** видимый фокус, все действия с клавиатуры, кнопки во время запроса не теряют фокус и не нажимаются второй раз.

Проверено в браузере на 1440x900 (контент `min(1120px, 100% - 64px)` по центру, цвета и размеры по макету) и на ширине 390px: таблицы превращаются в карточки, горизонтальной прокрутки нет. Автотестов интерфейса нет.

## Компромиссы и решения

- **Встроенный PostgreSQL вместо системного.** `npm run db:start` поднимает настоящий PostgreSQL 18 из npm-пакета: без установки в систему, без прав администратора, без Docker, с данными в каталоге проекта. Свой PostgreSQL подключается через `DATABASE_URL`.
- **SQL руками, без ORM.** Ключевые гарантии живут в SQL и должны быть видны: частичный уникальный индекс, условные `update ... where status = ...`, `for update skip locked`, блокировки строк в определённом порядке (заявка, затем ресурс, затем задача). Миграции: SQL-файлы и небольшой раннер с таблицей применённых версий и advisory lock.
- **Обработчик в процессе API, опрос базы вместо брокера.** Очередь это таблица `provider_jobs`. Для одного провайдера и десятков заявок брокер добавил бы инфраструктуру без пользы. Несколько процессов API могут работать с одной базой: захват `skip locked` и аренда не дают взять одну задачу дважды (но см. ограничения: это не проверено тестом).
- **NestJS 11 и TypeScript 5.9 вместо последних версий.** Новая основная ветка NestJS поставляется только как ESM, а Jest с ESM работает ненадёжно. TypeScript оставлен на ветке 5.x, с которой эта связка (NestJS 11, Jest, ts-jest) собирается и проходит тесты; TypeScript 7 не проверялся.
- **Cookie без флага `Secure` по умолчанию.** Приложение работает локально по http, с `Secure` браузер cookie не отправит. Для https включается `COOKIE_SECURE=true`. Сессии хранятся в базе (в cookie случайный токен, в базе его sha256), поэтому перезапуск API не разлогинивает.
- **Пароли в scrypt** из стандартной библиотеки Node, отдельный пакет не нужен. Для несуществующего логина проверка идёт по фиктивному хэшу, чтобы время ответа не выдавало, есть ли логин.
- **GET без ответа ведёт к повторному POST с тем же ключом, и попытка учитывается.** Если бы GET без ответа только откладывал задачу, при полном отказе провайдера заявка висела бы в `processing` вечно и не дошла бы до «Требует внимания». POST с тем же ключом и тем же телом безопасен: провайдер вернёт уже сохранённую операцию.
- **Попытка учитывается до отправки.** Если процесс падает между записью попытки и POST, попытка считается израсходованной, хотя запрос не ушёл. Поэтому до «Требует внимания» реальных POST может уйти меньше `PROVIDER_MAX_POST_ATTEMPTS`. Обратный порядок (сначала POST, потом запись) при падении терял бы факт отправки и мог бы дать лишний POST; выбран недосчёт, а не дубль.
- **30 дней передаются провайдеру как `period_months: 1`.** Имитатор принимает период только в месяцах. Срок ресурса при этом сдвигается ровно на 30 календарных дней по снимку заявки, а не на месяц.
- **Интерфейс отдаёт Vite.** Отдельной production-раздачи статики через API нет: `npm run dev` или `npm run preview -w apps/web` с прокси `/api`.

## Незавершённое и известные ограничения

- Остановка `npm run db:start` по Ctrl+C в живом терминале не проверялась; проверена остановка через `npm run db:stop`.
- `docker-compose.yml` не запускался ни разу.
- Нет тестов на остановку приложения посреди висящего запроса к провайдеру и на два обработчика в разных процессах. Логика аренды проверена в одном процессе (тест с живой и просроченной арендой).
- Нет автотестов интерфейса: он проверен руками в браузере.
- Сверка валюты со снимком при одобрении в коде есть, но тестом не покрыта: база не даёт поставить ресурсу валюту, отличную от RUB.
- Из «Требует внимания» по постоянной причине (`resource_changed`, `provider_mismatch`, `http_409`, `http_400`) повтор не выводит: ключ и тело прежние, провайдер ответит так же, и заявка вернётся в «Требует внимания». Других переходов из этого состояния нет, задание их не даёт; разрешить такую заявку можно только руками в базе. Для `resource_changed` интерфейс об этом предупреждает.
- Ресурс в `needs_attention` остаётся занятым, пока согласующий не доведёт повтор до завершения. Отменить или закрыть такую заявку нельзя.
- На Windows после Ctrl+C у `npm run dev` иногда остаётся процесс `node`, который держит порт 3000 или 5173; его нужно завершить вручную.
- Счётчик неудачных входов живёт в памяти процесса: у нескольких процессов API он свой у каждого, при перезапуске обнуляется.
- Проверка `Origin` сравнивает его с `Host`. За прокси, который подменяет `Host`, свои запросы получали бы 403; для такого развёртывания нужен список разрешённых адресов, его нет.
- Повторять сценарий проверки нужно с `npm run db:reset` и перезапуском имитатора. `npm run db:seed` возвращает сроки ресурсов, но заявки не трогает: активная заявка останется и не даст создать новую.
- Запуск проверен только на Windows 10. На Linux и macOS встроенный PostgreSQL ставится своим платформенным пакетом, а `npm run simulator` и тесты берут `python3`, затем `python`, но это не проверялось.
- Нет того, что сознательно не входило в задачу: регистрации, SSO, уведомлений, развёртывания, отмены заявки инициатором, редактирования ресурсов через интерфейс.
