# Контракт API

Базовый путь `/api`. Тела запросов и ответов JSON. Даты (`expiresOn`, `oldExpiresOn`, `newExpiresOn`) строкой `YYYY-MM-DD`, моменты времени (`createdAt` и подобные) строкой ISO 8601 в UTC. Суммы целым числом копеек (`amountMinor`, `priceMinor`), валюта `RUB`.

## Авторизация

Вход ставит cookie `renewals_session` (`HttpOnly`, `SameSite=Lax`, `Path=/`, срок 7 дней). Браузер отправляет её сам, на клиенте с ней ничего делать не нужно: в `fetch` достаточно `credentials: 'include'` (или `same-origin`, если интерфейс и API на одном адресе через прокси). Прочитать cookie из JavaScript нельзя, текущего пользователя узнают через `GET /api/auth/me`.

Все маршруты, кроме `POST /api/auth/login` и `GET /api/health`, без действующей сессии отдают 401. Пользователь и его права берутся только из сессии: поля вроде `userId` или `workspaceId` в теле и query сервер не читает.

## Ошибки

Любая ошибка приходит в одном формате:

```json
{ "error": "forbidden", "message": "Нет доступа к этому ресурсу" }
```

`message` написан для человека по-русски, его можно показывать как есть. Ветвиться в коде нужно по `error`.

| HTTP | `error` | Когда |
|---|---|---|
| 400 | `validation_error` | тело запроса неверное (нет полей, битый JSON) |
| 401 | `unauthorized` | нет сессии, сессия истекла, неверный логин или пароль |
| 403 | `forbidden` | чужое пространство или нет нужного права |
| 404 | `not_found` | нет такого ресурса, заявки или маршрута |
| 409 | `active_request_exists` | у ресурса уже есть активная заявка |
| 409 | `invalid_transition` | действие недопустимо в текущем состоянии заявки (повторное одобрение, одобрение отклонённой, отклонение одобренной, повтор заявки не в `needs_attention`) |
| 409 | `resource_changed` | при одобрении срок или стоимость ресурса не совпали со снимком в заявке |
| 409 | `conflict` | прочий конфликт состояния |
| 500 | `internal_error` | сбой на сервере, подробности только в логе |

## Модели

### Пользователь и членство

```json
{
  "user": { "id": "usr-universal-alpha", "login": "universal.alpha", "displayName": "Универсальный Alpha" },
  "memberships": [
    { "workspaceId": "ws-alpha", "workspaceName": "Alpha", "canInitiate": true, "canApprove": true }
  ]
}
```

### Ресурс

```json
{
  "id": "res-a-01",
  "workspaceId": "ws-alpha",
  "workspaceName": "Alpha",
  "name": "Хранилище A",
  "expiresOn": "2027-03-01",
  "priceMinor": 128000,
  "currency": "RUB",
  "activeRequest": { "id": "5f0c...", "status": "pending" },
  "canCreateRequest": false
}
```

- `activeRequest`: активная заявка ресурса (`pending`, `processing`, `needs_attention`) или `null`.
- `canCreateRequest`: у пользователя есть право инициатора в пространстве ресурса и нет активной заявки. Показывать кнопку «Продлить» только при `true`.

### Заявка

```json
{
  "id": "5f0c2a7e-3a51-4f0e-9a43-0d8d3c1b2e11",
  "workspaceId": "ws-alpha",
  "resourceId": "res-a-01",
  "resourceName": "Хранилище A",
  "status": "pending",
  "createdBy": { "id": "usr-initiator-alpha", "displayName": "Инициатор Alpha" },
  "decidedBy": null,
  "oldExpiresOn": "2027-03-01",
  "newExpiresOn": "2027-03-31",
  "amountMinor": 128000,
  "currency": "RUB",
  "idempotencyKey": "renewal-5f0c2a7e-3a51-4f0e-9a43-0d8d3c1b2e11",
  "providerOperationId": null,
  "lastErrorCode": null,
  "createdAt": "2026-11-11T09:30:00.000Z",
  "decidedAt": null,
  "completedAt": null,
  "canApprove": false,
  "canReject": false,
  "canRetry": false
}
```

- `status`: `pending` (на согласовании), `rejected` (отклонена), `processing` (выполняется), `completed` (завершена), `needs_attention` (требует внимания).
- `decidedBy`: кто одобрил или отклонил, либо `null`.
- `oldExpiresOn`, `newExpiresOn`, `amountMinor`: снимок на момент создания, дальше не меняются.
- `idempotencyKey`: ключ операции у провайдера (`renewal-<id>`), постоянный. Повтор после `needs_attention` идёт с тем же ключом. По нему операцию можно найти у провайдера: `GET /renewals/{idempotencyKey}`.
- `providerOperationId`: `operation_id`, который вернул провайдер, или `null`. Заполняется при завершении (`completed`). Бывает заполнен и у `needs_attention` с кодом `resource_changed`: провайдер операцию выполнил, но срок ресурса не сдвинут.
- `lastErrorCode`: короткий код последней проблемы с провайдером или `null`. Пока заявка `processing`, это код последней неудачной попытки (заявка ещё может завершиться сама); у `needs_attention` это причина остановки. Обнуляется при завершении и при повторе. Коды перечислены ниже.
- `canApprove`, `canReject`: у пользователя право согласующего в пространстве, заявка не его, статус `pending`.
- `canRetry`: то же право, заявка не его, статус `needs_attention`.

#### Коды `lastErrorCode`

| Код | Что значит | Что дальше |
|---|---|---|
| `http_503`, `http_5xx` | провайдер ответил ошибкой сервера, результат неизвестен | обработчик сам повторит через паузу с тем же ключом |
| `timeout` | провайдер не ответил за `PROVIDER_TIMEOUT_MS`, результат неизвестен | то же |
| `network_error` | соединение не установилось или оборвалось, результат неизвестен | то же |
| `bad_response` | ответ 200, но тело не читается как операция, результат неизвестен | то же |
| `attempts_exhausted` | `PROVIDER_MAX_POST_ATTEMPTS` попыток POST без подтверждения, последний GET тоже | `needs_attention`, нужен повтор согласующим |
| `http_409`, `http_400`, прочие `http_4xx` | провайдер отказал (например, тот же ключ с другим телом); повторять с тем же телом бессмысленно | `needs_attention` сразу после этой попытки |
| `provider_mismatch` | подтверждение пришло, но `resource_id`, сумма, валюта, период (`period_months`) или статус операции не совпали с заявкой | `needs_attention`, срок не сдвинут |
| `resource_changed` | провайдер подтвердил, но срок ресурса к этому моменту уже не равен `oldExpiresOn` | `needs_attention`, срок не сдвинут, `providerOperationId` заполнен |

Полный ответ провайдера, его заголовки и тело в заявку, историю и лог не попадают, только эти коды и `operation_id`.

### Событие истории

```json
{
  "id": 12,
  "actor": { "id": "usr-initiator-alpha", "displayName": "Инициатор Alpha" },
  "fromStatus": null,
  "toStatus": "pending",
  "kind": "created",
  "detail": null,
  "createdAt": "2026-11-11T09:30:00.000Z"
}
```

- `actor`: `null`, если переход сделала система (фоновый обработчик).
- `kind`: вид события:
  - `created`: заявка создана, `null -> pending`, автор инициатор;
  - `approved`: одобрена, `pending -> processing`, автор согласующий;
  - `rejected`: отклонена, `pending -> rejected`, автор согласующий;
  - `provider_error`: попытка POST без результата (503, таймаут, обрыв), статус не меняется: `processing -> processing`, автор система, `detail` вида `http_503, попытка 1 из 3`;
  - `completed`: провайдер подтвердил, срок сдвинут, `processing -> completed`, автор система, `detail` вида `operation_id <id>`;
  - `needs_attention`: подтверждения нет или оно не годится, `processing -> needs_attention`, автор система, `detail` это код причины (`attempts_exhausted`, `http_409`, `provider_mismatch`, `resource_changed` и т.п.);
  - `retry_requested`: повтор, `needs_attention -> processing`, автор согласующий.

  Интерфейсу незнакомый `kind` нужно показывать как есть, а не падать.
- Неудачные попытки (401, 403, 404, 409) событий не пишут и состояние заявки не меняют.
- `detail`: короткое пояснение или `null`.

## Маршруты

### POST /api/auth/login

Кто: любой, без сессии.

Тело:

```json
{ "login": "initiator.alpha", "password": "renewals-demo" }
```

Ответ 200: пользователь и членства (как у `GET /api/auth/me`) и заголовок `Set-Cookie` с сессией.

Ошибки: 400 `validation_error` (нет логина или пароля, не строки, длиннее 200 символов, битый JSON); 401 `unauthorized` с текстом «Неверный логин или пароль», одинаковым для неверного пароля и несуществующего логина.

### POST /api/auth/logout

Кто: вошедший пользователь. Тела нет.

Ответ 204 без тела: сессия удалена, cookie сброшен.

Ошибки: 401 без сессии.

### GET /api/auth/me

Кто: вошедший пользователь.

Ответ 200: пользователь и членства (модель выше).

Ошибки: 401.

### GET /api/resources

Кто: вошедший пользователь. Отдаются ресурсы только тех пространств, где у него есть членство.

Ответ 200: массив ресурсов, порядок по имени пространства, затем по `id`.

```json
[
  { "id": "res-a-01", "workspaceId": "ws-alpha", "workspaceName": "Alpha", "name": "Хранилище A", "expiresOn": "2027-03-01", "priceMinor": 128000, "currency": "RUB", "activeRequest": null, "canCreateRequest": true },
  { "id": "res-a-02", "workspaceId": "ws-alpha", "workspaceName": "Alpha", "name": "Сервис B", "expiresOn": "2027-05-20", "priceMinor": 250000, "currency": "RUB", "activeRequest": null, "canCreateRequest": true }
]
```

Ошибки: 401.

### GET /api/resources/:id

Кто: член пространства ресурса.

Ответ 200: ресурс и все его заявки, новые сверху.

```json
{
  "resource": { "id": "res-a-01", "...": "модель ресурса" },
  "requests": [ { "id": "5f0c...", "...": "модель заявки" } ]
}
```

Ошибки: 401; 403 `forbidden` (ресурс чужого пространства); 404 `not_found` (нет такого ресурса).

### POST /api/resources/:id/renewal-requests

Кто: пользователь с правом инициатора (`canInitiate`) в пространстве ресурса. Согласующий без этого права и пользователь чужого пространства получают 403.

Тело не нужно; если оно есть, сервер его игнорирует. Сумма, даты, автор и ключ задаются только сервером: снимок срока и стоимости ресурса, новый срок `expiresOn + 30` календарных дней, статус `pending`, автор из сессии. Срок ресурса при создании не меняется.

Ответ 201: созданная заявка (модель выше).

Ошибки: 401; 403 `forbidden`; 404 `not_found` (нет ресурса); 409 `active_request_exists` (у ресурса уже есть заявка в `pending`, `processing` или `needs_attention`).

### GET /api/renewal-requests

Кто: вошедший пользователь. Отдаются заявки только его пространств.

Ответ 200: массив заявок, новые сверху.

Ошибки: 401.

### GET /api/renewal-requests/:id

Кто: член пространства заявки.

Ответ 200: заявка и её события по порядку (старые сверху).

```json
{
  "request": { "id": "5f0c...", "...": "модель заявки" },
  "events": [ { "id": 12, "...": "модель события" } ]
}
```

Ошибки: 401; 403 `forbidden` (заявка чужого пространства); 404 `not_found` (нет такой заявки или `id` не uuid).

### POST /api/renewal-requests/:id/approve

Кто: пользователь с правом согласующего (`canApprove`) в пространстве заявки, если заявка не его. Универсальный пользователь свою заявку одобрить не может.

Тело не нужно; если оно есть, сервер его игнорирует (`decidedBy`, `status` и подобные поля не читаются).

Что происходит, одной транзакцией: заявка блокируется, срок и стоимость ресурса сверяются со снимком в заявке (`oldExpiresOn`, `amountMinor`, валюта), заявка переходит `pending -> processing`, записываются `decidedBy` и `decidedAt`, ставится задача отправки провайдеру и событие `approved`. Либо всё это, либо ничего. Срок ресурса здесь не меняется: его сдвигает только подтверждение провайдера.

Ответ 200: заявка (модель выше) в статусе `processing`.

Ошибки, проверки идут в этом порядке:

- 401 `unauthorized`: нет сессии;
- 404 `not_found`: нет такой заявки или `id` не uuid;
- 403 `forbidden`: заявка чужого пространства, нет права согласующего, своя заявка;
- 409 `invalid_transition`: заявка не в `pending` (уже одобрена, отклонена, выполняется). Из параллельных одобрений одной заявки успешно ровно одно, остальные получают этот код;
- 409 `resource_changed`: срок или стоимость ресурса изменились после создания заявки. Заявка остаётся `pending`, провайдер не вызывается. Её можно отклонить и создать новую со свежим снимком.

Сначала доступ (403), потом состояние (409): пользователь без права не узнаёт, в каком состоянии чужая заявка.

### POST /api/renewal-requests/:id/reject

Кто: как у `approve`: право согласующего в пространстве заявки, заявка не своя.

Тело не нужно; если оно есть, сервер его игнорирует.

Что происходит, одной транзакцией: заявка `pending -> rejected`, записываются `decidedBy` и `decidedAt`, событие `rejected`. Провайдер не вызывается, задача не ставится, срок ресурса не меняется. После отклонения ресурс свободен для новой заявки.

Ответ 200: заявка (модель выше) в статусе `rejected`.

Ошибки в том же порядке: 401 `unauthorized`; 404 `not_found`; 403 `forbidden` (чужое пространство, нет права, своя заявка); 409 `invalid_transition` (заявка не в `pending`).

### POST /api/renewal-requests/:id/retry

Кто: как у `approve`: право согласующего в пространстве заявки, заявка не своя.

Тело не нужно; если оно есть, сервер его игнорирует.

Что происходит, одной транзакцией: заявка `needs_attention -> processing`, `lastErrorCode` обнуляется, задача отправки снова ставится в очередь со счётчиком попыток POST с нуля, событие `retry_requested`. `decidedBy` и `decidedAt` не меняются: это по-прежнему решение того, кто одобрил. Ключ и тело запроса к провайдеру прежние, поэтому вторая операция у провайдера не появляется. Первым шагом обработчик спрашивает провайдера `GET` по ключу: если операция уже выполнена, заявка завершается без нового `POST`.

Ответ 200: заявка (модель выше) в статусе `processing`.

Ошибки в том же порядке, что у `approve`: 401 `unauthorized`; 404 `not_found`; 403 `forbidden` (чужое пространство, нет права, своя заявка); 409 `invalid_transition` (заявка не в `needs_attention`).

## Фоновый обработчик

Работает в том же процессе, что и API (`WORKER_ENABLED`, по умолчанию включён). Раз в `WORKER_POLL_MS` берёт готовую задачу в аренду на `WORKER_LEASE_MS` и делает шаг:

1. Если POST уже уходил (или это повтор), сначала `GET /renewals/{ключ}`. Операция есть: завершение.
2. Попытка POST записывается в базу, потом уходит `POST /renewals` с `Idempotency-Key` и телом из снимка заявки.
3. 200: завершение. 503, таймаут, обрыв: событие `provider_error`, следующий шаг через `PROVIDER_RETRY_DELAY_MS`. 4xx: `needs_attention`.
4. После `PROVIDER_MAX_POST_ATTEMPTS` попыток без подтверждения и последнего `GET`: `needs_attention`.

Завершение одной транзакцией: заявка `completed`, `providerOperationId`, срок ресурса `oldExpiresOn -> newExpiresOn`, задача закрыта, событие `completed`. Повторная обработка срок не сдвигает: заявка уже не `processing`. Состояние задачи живёт в базе, поэтому после перезапуска обработчик продолжает с того же места тем же ключом.

### GET /api/health

Кто: любой, без сессии.

Ответ 200: `{ "status": "ok", "database": "up" }`. Если база не отвечает: 503 `{ "error": "database_unavailable", "message": "База данных недоступна" }`.
