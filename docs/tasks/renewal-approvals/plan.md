# План: renewal-approvals

Статус: утверждён 2026-11-11.

Ведение работы: командная сессия раздаёт фичи субагентам или младшим сессиям, сама код не пишет, проверяет результат и ведёт `features.md` и `progress.md`.

Модель исполнителей: Opus (в вызове Agent `model: "opus"`, в младшей сессии `claude-opus-5-5`), не Fable. Решение Данияра от 2026-11-11: Fable съедает лимиты. Командная сессия остаётся на своей модели.

Каркас: работа на несколько сессий. Спека в `spec.md`, фичи в `features.md`, журнал в `progress.md`.

## Окружение

- Node 24, npm 11, Python 3.14 (имитатор). На этой машине команда `python`, не `python3`.
- PostgreSQL встроенный: пакет `embedded-postgres` как dev-зависимость, настоящие бинарники PostgreSQL, данные в игнорируемом каталоге проекта. Запуск одной командой `npm run db:start`, без установки в систему и без прав администратора. Пакет проверен в реестре 2026-11-11: создан в 2022, 1,8 млн загрузок в неделю. Системного PostgreSQL на машине нет: установщик остановлен на шаге с паролем.
- Приложение подключается по `DATABASE_URL`, поэтому проверяющий может подставить и свой PostgreSQL.
- Имитатор слушает фиксированный порт 8091. Тесты с имитатором нельзя гонять одновременно в двух местах.
- Docker на машине нет. `docker-compose.yml` для базы кладётся как запасной путь и помечается в README как непроверенный.
- Базы: `renewals` (приложение), `renewals_test` (тесты). Роль приложения тестовая, её данные открыто в README и `.env.example`.

## Решения

### Доступ к базе

Драйвер `pg` и SQL руками, без ORM. Причина: правило одной активной заявки это частичный уникальный индекс, переходы состояний это условные `UPDATE ... WHERE status = ...`, обработчик берёт задачи через `FOR UPDATE SKIP LOCKED`. Всё это в SQL видно напрямую, ORM это только прячет. Миграции: SQL-файлы и маленький собственный раннер с таблицей применённых версий.

### Схема

- `workspaces(id, name)`
- `users(id, login unique, password_hash, display_name)`
- `memberships(user_id, workspace_id, can_initiate, can_approve)`, первичный ключ по паре
- `resources(id, workspace_id, name, expires_on date, price_minor integer, currency check = 'RUB')`
- `renewal_requests(id uuid, workspace_id, resource_id, status, created_by, decided_by, old_expires_on, new_expires_on, amount_minor, currency, idempotency_key unique, provider_operation_id, last_error_code, created_at, decided_at, completed_at)`
  - уникальный индекс по `resource_id` с условием `status in ('pending','processing','needs_attention')`
  - `check (decided_by is null or decided_by <> created_by)` как второй рубеж запрета на свою заявку
- `request_events(id, request_id, actor_user_id null для системы, from_status, to_status, kind, detail, created_at)`
- `provider_jobs(id, request_id unique, post_attempts, state, next_run_at, lease_until, created_at, updated_at)`
  - `request_id unique` не даёт завести вторую задачу на одну заявку
- `sessions(token_hash, user_id, expires_at)`

### Авторизация

Логин и пароль, пароль хэшируется `scrypt` из стандартной библиотеки Node. Сессия в базе, в cookie случайный токен: `HttpOnly`, `SameSite=Lax`. Сессии в базе, чтобы перезапуск приложения в контрольном сценарии не разлогинивал.

Права проверяет guard: пользователь из сессии, членство и роль из `memberships`. Пространство берётся из самой сущности (ресурс или заявка), а не из запроса. Чужой ресурс или заявка по ID: 403, как требует задание. Несуществующий ID: 404.

### Создание заявки

Одна транзакция: блокировка строки ресурса, снимок срока и стоимости, `new_expires_on = expires_on + 30`, вставка заявки и события. Нарушение частичного индекса превращается в 409.

Ключ идемпотентности: `renewal-<id заявки>`, создаётся вместе с заявкой и никогда не меняется.

### Одобрение и отклонение

Одна транзакция:

1. `select ... for update` строки заявки. Не `pending`: 409.
2. Автор заявки равен текущему пользователю: 403.
3. Для одобрения: блокировка ресурса, сверка срока и стоимости со снимком. Расхождение: 409, заявка остаётся `pending`, её можно отклонить и создать новую.
4. Смена статуса, вставка задачи в `provider_jobs`, событие в историю.

Параллельные одобрения сериализуются блокировкой строки: второй видит уже не `pending` и получает 409.

### Обработчик

Цикл опроса в том же процессе, интервал настраивается. Захват задачи: `FOR UPDATE SKIP LOCKED` плюс аренда `lease_until`, чтобы упавший процесс не оставил задачу навсегда занятой.

Шаги по задаче:

1. Если `post_attempts > 0`, сначала `GET /renewals/{ключ}`. Ответ 200 и `completed`: финализация. 404: идём к POST.
2. Перед POST в отдельной транзакции `post_attempts += 1`. Сначала запись, потом отправка: падение после отправки не теряет факт попытки.
3. POST с тем же ключом и телом из снимка заявки.
   - 200: финализация.
   - 503, таймаут, обрыв сети: `next_run_at = now + PROVIDER_RETRY_DELAY_MS`. Это и есть окно, в которое приложение можно остановить.
   - 409 или 400 от провайдера: сразу `needs_attention`, повтор автоматически бессмыслен.
4. `post_attempts = 3` и подтверждения нет (последний GET тоже не дал результата): `needs_attention`.

Финализация одной транзакцией: `update renewal_requests set status = 'completed' where id = ... and status = 'processing'`. Только если строка обновилась: `update resources set expires_on = new_expires_on where id = ... and expires_on = old_expires_on`, задача закрывается, событие в историю. Повторная обработка не находит заявку в `processing` и ничего не делает.

Ответ провайдера сверяется с заявкой по `resource_id` и сумме. В лог и в историю идут только код результата и `operation_id`.

Повтор согласующим: `needs_attention -> processing`, счётчик попыток обнуляется, ключ прежний. Свою заявку повторять нельзя по тому же правилу, что и согласовывать.

### API

```
POST /api/auth/login
POST /api/auth/logout
GET  /api/auth/me
GET  /api/resources
GET  /api/resources/:id                       ресурс и история его заявок
POST /api/resources/:id/renewal-requests
GET  /api/renewal-requests
GET  /api/renewal-requests/:id                заявка и события
POST /api/renewal-requests/:id/approve
POST /api/renewal-requests/:id/reject
POST /api/renewal-requests/:id/retry
```

Ошибки единым форматом: `{ "error": "<код>", "message": "<текст для человека>" }`.

### Интерфейс

React, Vite, обычный CSS с переменными под цвета макета. Страницы: вход, список ресурсов и заявок (экран из макета), карточка заявки с историей и действиями. Пока есть заявки в `processing`, список сам обновляется опросом. На 390px таблица превращается в карточки.

### Тесты

Jest и supertest против поднятого приложения, настоящей базы `renewals_test` и настоящего имитатора, который тесты запускают сами. Для «Требует внимания» отдельная заглушка провайдера, которая всегда отвечает 503 и 404, потому что настоящий имитатор подтверждает уже на втором запросе. Восстановление после сбоя проверяется остановкой и новым запуском приложения внутри теста при работающем имитаторе.

## Настройки

| Переменная | Значение по умолчанию | Смысл |
|---|---|---|
| `DATABASE_URL` | локальная база `renewals` | подключение |
| `PROVIDER_BASE_URL` | `http://127.0.0.1:8091` | адрес имитатора |
| `PROVIDER_RETRY_DELAY_MS` | `15000` | пауза после 503 перед GET или повторным POST |
| `PROVIDER_TIMEOUT_MS` | `5000` | таймаут запроса к провайдеру |
| `WORKER_POLL_MS` | `1000` | интервал опроса задач |
| `PROVIDER_MAX_POST_ATTEMPTS` | `3` | попыток POST до «Требует внимания» |
